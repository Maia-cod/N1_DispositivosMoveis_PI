Arquitetura em Camadas — BarberAgenda
Padrão de separação de responsabilidades: Apresentação → Negócio → Dados → Persistência

1. Camada de Apresentação (UI) — Android

LoginActivityautenticação / sessão
MainActivityagenda + busca
CadastroActivitynovo agendamento
DetalheActivitydetalhe / status
AgendamentoAdapterRecyclerView + ViewHolder
Layouts XMLConstraintLayout + Material 3
View Bindingacesso tipado às views
▼ chama validações / regras  ·  ▲ recebe resultado

2. Camada de Negócio

RegrasNegociologin, cliente, telefone, horário, conflito, cancelamento
▼ solicita operação de dados (main → thread de E/S)  ·  ▲ callback / LiveData

3. Camada de Dados (repositório)

AgendamentoRepositoryExecutorService + Handler (main thread)
SessaoSharedPreferences (login / perfil)
▼ consulta / insere / atualiza  ·  ▲ LiveData<List<Agendamento>>

4. Persistência local

AppDatabaseRoomDatabase (singleton)
AgendamentoDao@Insert @Update @Query
UsuarioDaoautenticar / inserir
ModelsUsuario · Agendamento (@Entity)
SQLitebarberagenda.db
Decisões técnicas: operações de banco rodam fora da main thread (ExecutorService) e retornam via Handler(Looper.getMainLooper()); a listagem usa LiveData (Observer atento ao ciclo de vida) para atualizar a UI automaticamente. A UI nunca acessa o banco diretamente — sempre pela camada de negócio/repositório. Persistência 100% local (Room/SQLite), o que garante funcionamento sem conectividade.
